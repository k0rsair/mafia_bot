# Republish lobby control with buttons from /mafia_status

**Date:** 2026-08-22 20:26
**Files:** src/bot/commands/lobbyCommands.ts, src/application/LobbyService.ts, src/infrastructure/repositories/GameRepository.ts, tests/unit/bot/lobbyCommands.test.ts, tests/unit/application/lobbyService.test.ts, docs/manual-acceptance-checklist.md
**Severity:** medium

## Problem

With an open lobby, `/mafia_status` sent a new lobby message that looked like the real control but had no inline keyboard. Players could not join, leave, or start from that message.

## Root Cause

`renderLobby` already returns both `text` and `replyMarkup`. The `/mafia` path and join/leave callbacks pass `reply_markup` through `editLobbyMessage`. The `/mafia_status` command path called `context.reply(renderLobby(...).text)` and dropped the keyboard. The command also never updated `lobbyMessageId`, so even a later keyboard would have left join/leave editing the original `/mafia` message.

This is the same command-vs-callback gap as city-vote publication: the callback/edit path was complete, the command republish path was not.

## Solution

`/mafia_status` now replies with the full lobby view, including join/leave/start buttons, and stores the new message id via `LobbyService.recordLobbyMessage` / `GameRepository.setLobbyMessageId`. Subsequent membership edits target the republished control, matching `republishCurrentControl` for later phases. `[FIX:lobby-status-control]` logs only game id, phase, and player count.

## Prevention

- Any command that republishes a control must send `text` and `reply_markup` from the same renderer used by create/edit paths.
- When a control is republished, persist its message id so later edits do not update a stale original.
- Cover the command path with a unit test that asserts the keyboard callback data, not only the text.
