# Fix: personal city-vote panels

## Problem

The shared city-vote message showed every player's stateful choice and confirmation buttons. A player could therefore see a stale-looking choice in the common message, have their own selection apparently disappear after pressing a candidate, and only see the value once confirmation refreshed the shared control.

## Root Cause

Telegram inline keyboards and message text belong to one shared chat message. They cannot render a different selected state or remove buttons only for the user who pressed them. Treating that public message as a personal form mixed global and per-player UI state.

## Solution

- Keep the public control as neutral progress and confirmed choices only.
- Deliver and restore one ephemeral personal panel per eligible real player for each city vote round.
- Persist draft selection before confirmation, redraw the same personal panel after selection, and clear its keyboard after confirmation.
- Refresh the public control through its durable stored message ID and continue closing a round automatically once every living player confirms.

## Prevention

For any per-user interaction in a group, model the state in storage and render it in a receiver-scoped panel. Shared messages must show only state that is safe and identical for every participant. Tests cover initial, draft, and confirmed panel states, automatic panel delivery, restoring a panel, and the completion path.
