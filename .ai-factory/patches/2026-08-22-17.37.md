# Personal city-vote panels instead of shared keyboard state

**Severity:** high

## Problem

The city vote window looked pre-selected when it opened. Clicking a candidate cleared the visible choice. Confirming then showed the chosen player. Expected: nothing selected at start; selecting shows who was chosen; confirming adds a checkmark next to that player and removes the buttons.

## Root Cause

Telegram inline keyboards and message text belong to one shared group message. They cannot show a different selected state or hide buttons only for the player who pressed them. `Vote.confirmedAt` already stored a two-step draft/confirm, but `renderVoteView` still put candidate and confirm buttons on the public control. After a click, `editMessageText` redrew that shared message without the player's draft, so the client's brief pressed-state disappeared. Confirmed rows, including virtual test votes, appeared in «Кто за кого» and read as “I already voted.”

A previous personal-panel implementation was reverted. Blindly restoring it would have reintroduced `confirmed: vote?.confirmedAt !== null`, which is true when `vote` is null (`undefined !== null`) and would open an empty panel as already confirmed.

## Solution

City votes now use the same receiver-scoped ephemeral pattern as the mafia council:

- Public control shows only progress, confirmed «кто за кого» rows with `✅`, and `🗳️ Открыть моё голосование`.
- `VotePanelService` delivers, opens, refreshes, and restores a personal panel per living non-virtual player.
- Empty: `Ваш выбор: —`. Draft: `Ваш выбор: <имя> ⏳` plus confirm. Confirmed: `Ваш выбор: <имя> ✅` and an empty keyboard.
- `getVotePanelState` treats a missing vote as `selectedChoice: null` and `confirmed: false` (`vote !== null && vote.confirmedAt !== null`). The displayed name comes from the current round's candidates.
- Candidate clicks refresh the ephemeral panel. The public control is edited by `controlMessageId` only after a successful confirm.

`[FIX:city-vote-panel]` logs game, phase, version, confirmation flag, and delivery counts only.

## Prevention

- For any per-user interaction in a group, persist the choice and render it in a receiver-scoped panel. Shared messages must show only state that is identical for every participant.
- Never treat `optionalValue !== null` as a present-and-non-null check; `undefined !== null` is true. Prefer `value !== null && value.field !== null`.
- Cover empty, draft, and confirmed personal-panel states, including final-decision `all-leave` / `all-stay`, plus `/restore_panel` during `DAY_VOTE`.
- Do not `editMessageText` a public control from a personal-panel callback; use the stored `controlMessageId`.
